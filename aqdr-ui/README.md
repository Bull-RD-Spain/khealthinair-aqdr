# K-HEALTHinAIR AQDR Platform UI

The AQDR UI is a Grafana instance customized for the K-HEALTHinAIR project.
This is achieved by building a custom docker image based on the grafana-oss
release and making some changes and adding initialization scripts, along with
the provision of datasource and dashboard configuration.

The deployment can be done using docker-compose or kubernetes descriptors, so
slight adjustments are necessary in each case, to inject the necessary
environment variables and initialization configuration file.

## Customization

The customization is performed when building the custom docker image (aqdr-ui)
within the Dockerfile, by adding the alternative styles, and including other
provisioning and configuration files (most under `apdr-ui/conf`).
For extended configuration, when via arguments is not possible, providing a
complete `grafana.ini` file could be eventually needed, so it has been prepared
for it. The AQDR-UI image generated via de Dockerfile, includes the copy of the
`grafana.ini` customized with the proper ENV variables placeholders for custom
configuration like SMTP or Auth settings

## Initialization

When the container is started with the customized image, a script is executed
against the Grafana API for extra initialization, leaving the platform ready for
use.

### The aqdr-ui-init-conf.yaml init conf file

The Python script is expecting a specific yaml file containing the initialization,
`/aqdr-ui/grafana-initialization/aqdr-ui-init-conf.yaml`, with `organization`,
`users`, `teams` and `folder_permissions` sections, with the lists of users.

```yaml
organization:
  name: K-HEALTHinAIR
users:
  - login: -
    name: -
    email: -
    password: -
    orgId: 1
teams:
  - name: -
    members:
      - login: -
        permission: Admin
folder_permissions:
  - uid: pilot-at
    permissions:
      - userId: 1
        permission: 0
        role: Admin
      - teamId: 1
        permission: 0
        role: Editor
```

Depending on the
deployment mechanish could be mounted as volume from the host (docker compose),
or from a `secret` (since contains passwords) in Kubernetes, like in the
following example:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: aqdr-ui-secret
  namespace: khealthinair
type: Opaque
stringData:
  GF_SECURITY_ADMIN_PASSWORD: "************"
  KHIA_DSOURCE_AUTH_PASSWORD: "********"
  KHIA_DSOURCE_AUTH_TOKEN: "***********"
  AQDR_UI_INIT_CONFIG_FILE_YAML: |
    organization:
      name: K-HEALTHinAIR
    users:
      - login: -
        name: -
      ···
```

and then in the `deployment`, mount the file in the desired directory as
following:

```yaml
    ···
    volumeMounts:
    - name: aqdr-ui-config-volume
      mountPath: /aqdr-ui/grafana-initialization/
      readOnly: true
volumes:
- name: aqdr-ui-config-volume
  secret:
    secretName: aqdr-ui-secret
    items:
    - key: AQDR_UI_INIT_CONFIG_FILE_YAML
      path: aqdr-ui-init-conf.yaml
    ···
```

### Grafana REST API CLient

Under the `grafana-initialization` folder, where the initialization process
resides, the `grafana_client` module is a python API REST client automatically generated by the [OpenAPI Generator](https://openapi-generator.tech) project.
Grafana exposes an OpenAPI in the `http://localhost:3000/swagger |
http://localhost:3000/public/openapi3.json` endpoint, and this is used for the
specific version client generation. The client could be generated with just the
source code and skiping utility project files (generateSourceCodeOnly), although
it is useful to understand the necessary dependencies from a parent project.

Examples of generation:

```shell
docker pull openapitools/openapi-generator-cli
```

with

```shell
docker run --network="host" --rm --volume "K-HEALTHinAIR/khealthinair-aqdr/aqdr-ui/grafana-initialization:/temp" openapitools/openapi-generator-cli generate --generator-name python --input-spec "temp/openapi3-10.4.3.json" --output "/temp" --package-name "grafana_client" --additional-properties="generateSourceCodeOnly=true,projectName=khealthinair,dateFormat=%d/%m/%Y"
```

or, if running grafana already in a port, like 3000, directly from it

```shell
  docker run --network="host" --rm --volume "K-HEALTHinAIR/khealthinair-aqdr/aqdr-ui/grafana-initialization:/temp" openapitools/openapi-generator-cli generate --generator-name python -i http://localhost:3000/public/openapi3.json --output "/temp" --package-name "grafana_client" --additional-properties="generateSourceCodeOnly=true,projectName=khealthinair,dateFormat=%d/%m/%Y"
```

## Configuration

The environment variables expected by the image are common to the type of
mechanism chosen for the deployment, but the way to inject them into the
environment varies depending on whether docker-compose or Kubernetes is used.
For docker-compose `.env` file can be provided, while in deployments with
Kubernetes, the necessary configuration files must be created from secrets and
configmaps in the expected folders to be applied in advance.

The expected environmental variables are the following:

- APP_LOG_LEVEL: with the level of logs that will be printed within the file
  aqdr-ui-initialization.log (by default, "INFO").
- GF_SECURITY_ADMIN_USER: the grafana API user, for basic auth that should be
  and admin one (by default, "khealthinair_admin").
- GF_SECURITY_ADMIN_PASSWORD: the grafana API user password, for basic auth
- KHIA_DSOURCE_URL: The endpoint where the data source (aqdr-ts-db) is located
- KHIA_DSOURCE_AUTH_USER: The user for the data source (aqdr-ts-db)
- KHIA_DSOURCE_AUTH_PASSWORD: The password for the data source (aqdr-ts-db)
- KHIA_DSOURCE_AUTH_TOKEN: The token for the data source basic auth headers
- GF_DASHBOARDS_DEFAULT_HOME_DASHBOARD_PATH: The path to the provisioned home
  dashboard (e.g.: /var/lib/grafana/dashboards/default/0.home-page.json)
- GRAFANA_INGRESS_URL: the public url where the service is exposed for the
  Kubernetes resource Ingress (e.g.: "https://aqdr.k-healthinair.ari-health.eu")
- GRAFANA_API_ENDPOINT: Usually composed by ${GRAFANA_INGRESS_URL}/api
- GF_SNAPSHOTS_EXTERNAL_SNAPSHOT_NAME: The description text generated for the
  snapshot
- GF_SNAPSHOTS_EXTERNAL_SNAPSHOT_URL: Usually equals to ${GRAFANA_INGRESS_URL}
- GF_SMTP_ENABLED: Flag to enabling the SMPT service
- GF_SMTP_HOST: service endpoint, like smtp.titan.email:465 or
  mail-service.kube-system.svc.cluster.local:25
- GF_SMTP_USER: The onle to log into the service noreply@k-healthinair.eu
- GF_SMTP_PASSWORD: The password for the previous
- GF_SMTP_SKIP_VERIFY: Depending on the type of SMTP service
- GF_SMTP_FROM_ADDRESS: Like noreply@k-healthinair.eu

The `deployment` last configuration in included to enabling the
"Dashboard snapshots", which shares an interactive panel publicly while Grafana
strips sensitive data leaving only the visible metric data and series names
embedded in the dashboard.
This arguments are: GF_SNAPSHOTS_EXTERNAL_SNAPSHOT_NAME,
GF_SNAPSHOTS_EXTERNAL_SNAPSHOT_URL and GF_FEATURE_TOGGLES_ENABLE, the last one
included with fixed value in the Dockerfile. More info in
https://grafana.com/docs/grafana/latest/dashboards/share-dashboards-panels/#publish-a-snapshot
To check the smtp service, the service is in https://hostinger.titan.email/mail/
